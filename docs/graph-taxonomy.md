# 관계 taxonomy와 안정적인 그룹

이 문서는 지식 지도에서 관계와 묶음이 뜻하는 것, 목적별 그룹을 안정적으로 유지할 기준을 정의한다. 관계 목록과 현재 동작은 코드에서 확인한 계약이다. 코드는 기존 기록 묶음을 문서와 기록의 공동 목적 그룹으로 확장한다. 운영 자료 배정은 원문별 검토와 원문·정의 revision 확인을 거쳐 별도로 적용한다.

## 구축 배경

사용자는 지식과 작업 흐름 하나를 별로, 함께 쓰는 자료 군집을 은하로, 자료 사이의 연결을 별자리로 보고 싶어 우주 테마를 선택했다. 지도는 그 탐색 경험을 표현한다. 화면상 군집이나 거리가 자료의 의미 소속과 같다고 해석하지 않는다.

초기 개인 실험에서는 graph DB 탐색이 7 hop부터 유의미한 시간이 걸렸다는 사용자의 관찰이 있었다. 이는 개인 실험의 서사이며 엔진 전반의 성능 비교 결과가 아니다. 개인 사용 목적에 PostgreSQL이 맞는다는 판단으로 현재 저장 구조를 구축했다. 관계 수가 늘 때도 저장된 분류 ID·원문 revision·근거와 실제 조회 한도를 확인하며, 관계 표현의 어려움을 데이터베이스 교체만으로 해결했다고 보지 않는다.

별자리처럼 변하는 관계를 탐색하면서도 다시 찾을 목적 그룹은 저장한 기준으로 유지한다. 의미 개체의 세부 관계는 원문의 명시적 선언과 출처를 따르고, 문서 본문 링크나 시각적 근접을 의미 사실로 승격하지 않는다.

## 현재 관계의 정의

문서와 기록은 지식이다. 문서 태그·기록 묶음·회사 분야는 분류 표식이고, 폴더는 경로에서 계산한 구조다. 분류 표식이나 접힌 대표 별을 별도 지식으로 세지 않는다.

| 관계 | 방향·대상 | 정의 | 그룹 판단에서의 한계 |
| --- | --- | --- | --- |
| 관련 자료 (`related`) | 문서 ↔ 문서. 저장된 수동 연결은 정렬된 양 끝점으로 보관하며, native 연결은 원문에서 참조한 자료로 향한다. | 두 자료를 함께 탐색할 이유가 있는 연결. native의 명시적 `related`와 설정으로 선택한 본문 링크도 이 종류로 투영한다. | 같은 목적이나 같은 그룹이라는 뜻은 아니다. 원문 라우터의 많은 참조도 각각의 자료 연결이다. |
| 원문 링크 (`reference`) | 현재 문서 → 현재 문서 | 실제 Markdown 본문의 링크를 해석해, 현재 조회 범위에서 보이는 대상에 연결한다. 같은 저장소의 Git 경로나 native의 canonical scope/path로 해석하며 반복 링크는 한 연결이다. | 문서가 대상을 참조한다는 뜻이다. 같은 목적이나 주장의 근거를 추론하지 않는다. |
| 출처 근거 (`evidence`) | 기록 → 문서 또는 근거로 사용할 수 있는 기록 | 기록이 참조한 자료와 리비전·내용을 연결한다. 현재 근거와 과거 근거를 구분한다. | 관련 자료와 구별한다. 연결 자체가 기록의 모든 주장을 사실로 확정하거나 같은 그룹 소속을 뜻하지 않는다. |
| 문서 태그 (`topic`) | 문서 → 태그 | 문서를 찾는 복수의 주제 관점. 문서당 0~10개, 앱 범위별 이름·저장 ID를 가진다. | 여러 태그가 공존한다. 같은 태그 하나만으로 단일 목적 그룹을 확정하지 않는다. |
| 목적 묶음 (`subject`) | 문서 또는 기록 → 묶음 | 앱 범위마다 저장된 목적 ID와 자료당 0~1개의 소속을 가진다. | 자동 판정과 수동 확인을 구분한다. 문서와 개인 기록의 판단 정책은 각각의 계약을 따른다. |
| 회사 분야 (`area`) | 회사 문서 → 분야 | `meenseek` 문서를 5개 고정 사업 관점으로 분류한다. 복수 배정할 수 있다. | 업무 목적 그룹이나 개인 자료의 분류로 자동 치환하지 않는다. |
| 부모·소속 (`parent`) | 원문 또는 폴더 → 상위 폴더 | native scope와 경로에서 계산한 구조적 소속이다. | 사실 관계나 목적 소속이 아니다. 관계 군집 계산에서 제외한다. |

native 원문 안의 `ontology.relations`는 별도 층이다. 각 항목은 `from`·`type`·`to`로 두 의미 개체의 관계를 기술하며, 개체 ID는 `kind:name` 형식이다. 현재 `type`은 소문자 kebab-case 형식을 검증하고 의미별 허용 목록은 없다. 동일한 `from/type/to` 관계 항목의 중복은 금지하지만, 서로 다른 관계에서 같은 타입을 쓰는 것은 허용한다. 양 끝점의 형식 검증도 개체의 실재 참조나 주장 진실을 검증하는 것은 아니다. 예를 들어 테스트의 `supports`는 현재 Web 지도의 `evidence`와 자동으로 같은 뜻이 되지 않는다. 이 관계는 의미 개체 조회에서 출처 자료·리비전과 함께 반환하며, Web의 7종 자료 연결로 직접 표시하지 않는다.

추가 의미 관계를 도입할 때는 실제 사용 사례의 문장, 방향, 양 끝점의 대상, 근거 원문과 리비전, 같은 그룹을 뜻하는지 먼저 정의한다. 지원된다는 이유만으로 새로운 관계 이름이나 추측한 동의어를 대량 생성하지 않는다.

native의 다른 분류 축도 관계와 구분한다. `ontology: true`인 원문에서 다음 선택적 값을 검증한다.

| 축 | 현재 허용 값 | 의미 |
| --- | --- | --- |
| `type` | `project`, `business`, `decision`, `knowledge`, `writing`, `learning`, `entity` | 자료의 성격 |
| `domain` | `portfolio`, `product`, `business`, `engineering`, `writing`, `learning` | 자료를 다루는 영역 |
| `status` | `draft`, `active`, `archived` | 원문에 선언한 생애 상태 |
| `confidence` | `low`, `medium`, `high` | 원문에 선언한 확신 수준 |
| `entities` | `kind:name` 형식의 목록 | 자료에서 다루는 의미 개체 |
| `applies_to` | 비어 있지 않은 한 줄 값의 목록 | 적용할 맥락 |

원문의 `status`·`confidence`를 앱의 출처 확인 상태, 기록 저장 상태, 근거 검증 결과로 바꾸어 해석하지 않는다. `type`이나 `domain`만으로 같은 목적 소속을 추론하지 않는다. 앱의 `personal`·`meenseek` 조회 범위와 원문의 native scope도 별개이며, 조회 위치가 원문의 소속을 바꾸지 않는다.

## 의미 관계를 추가하기 전 진단

Native `context`의 `ontology-audit`는 지정한 원문과 이번 호출에 제공한 관계 정의를 대조하는 읽기 전용 진단이다. 원문·관계·분류·이력·검색 projection을 변경하지 않으며 관계 수락·진실 판단을 수행하지 않는다. DB 준비와 store identity 확인은 [AGENTS.md의 공통 시작](../AGENTS.md#공통-시작)을 따른다.

```json
{"op":"ontology-audit","scope":"personal","paths":["<실제 원문의 상대 경로>.md"]}
```

하나의 native scope에서 정확한 소문자 `.md` 경로 1~100개를 지정한다. 파일당 64 KiB, 전체 원문 bytes와 최종 JSON 응답 각각 1 MiB 상한을 적용한다. bytes와 store·material identity·revision·digest는 같은 SQL snapshot에서 읽는다. 기존 shared gate가 pending apply·복구를 막으며, 자료 하나라도 없거나 삭제·제한 상태, 형식 오류, 선언 scope 불일치이면 전체 선택이 실패한다. 일부 원문을 생략한 검사를 전체 결과로 반환하지 않는다. 검색 projection의 준비·재작성은 필요하지 않다.

`definitions` 생략 또는 `null`은 개체 목록·관계 종류·출처 조사다. 관계 정의를 제공했을 때만 그 기준의 방향별 대상 종류·자기 연결 조건을 검사한다. 빈 `definitions: []`는 정의가 하나도 없다는 기준을 명시적으로 제공한 경우다. 정의는 이번 호출의 진단 기준이며 새 정책·관계 사전으로 자동 저장하지 않는다.

| 정의 필드 | 뜻·제한 |
| --- | --- |
| `id` | 기존 소문자 kebab-case 관계 종류. 입력에서 중복할 수 없다. |
| `definition` | 관계 성립 조건을 설명하는 비어 있지 않은 한 줄, 최대 4,096 UTF-8 bytes. |
| `from_kinds`, `to_kinds` | 각 방향에서 허용하는 `kind:name`의 `kind` 목록 1~32개, 중복 없이 지정한다. |
| `allow_self` | 같은 개체를 양 끝점에 쓸 수 있는지 명시하는 boolean. |

정의는 최대 32개이며 기존 CLI의 32 KiB 요청 상한도 적용한다. 아래는 합성 예시이며 `depends-on`을 실제 관계 사전으로 채택한 결과가 아니다.

```json
{
  "op":"ontology-audit","scope":"personal",
  "paths":["<실제 원문의 상대 경로>.md"],
  "definitions":[{
    "id":"depends-on",
    "definition":"출발 프로젝트의 운영에 대상 시스템의 제공 또는 상태가 필요하다.",
    "from_kinds":["project"],"to_kinds":["system"],"allow_self":false
  }]
}
```

결과의 `sources`는 원문별 store ID, scope, 정확한 상대 경로, material ID, 현재 revision·content digest·byte length를 반환한다. 동일한 `from/type/to`는 한 관계로 모으되 모든 출처 경로를 보존한다. `assertions`·종류별 건수는 출처별 관계 항목 수이고 `relations`는 선택 안에서 중복을 모은 literal triple 목록이다. 비슷한 개체 이름·관계 동의어는 합치지 않는다.

`selection_digest`와 `criteria_digest`는 선택과 기준의 재현용 지문이다. 관계·개체·기준 문자열에는 기존 secret redaction을 적용하며 값이 바뀌면 `redacted: true`다. 호출자가 선택한 출처 경로와 그 참조는 정확히 유지해 `sources`의 원문 근거와 연결한다. 지문은 redaction 전 값에 결합되고, 가려진 출력만으로 개체 동일성을 판단하지 않는다. 원문 본문은 출력하지 않는다.

| 진단 코드 | 해석 |
| --- | --- |
| `endpoint-not-listed-in-selected-entities` | 끝점이 선택한 원문들의 `entities` 목록에 없다. 이 목록은 다루는 개체를 뜻하며, 누락 자체는 원문 오류나 전역 개체 부재 판정이 아니다. |
| `duplicate-entity-declaration` | 같은 원문의 `entities` 목록에 같은 ID가 반복된다. |
| `relation-type-not-defined-in-input` | 제공한 정의 목록에 관계 종류가 없다. 기존 관계를 잘못됐다고 확정하지 않는다. |
| `source-kind-not-allowed`, `target-kind-not-allowed` | 정의의 방향별 대상 종류와 끝점의 종류가 다르다. |
| `self-relation-not-allowed` | 정의는 자기 연결을 허용하지 않지만 양 끝점이 같다. |

결과는 의미 검토의 시작점이다. 정의의 타당성, 원문이 관계를 실제로 주장하는지, 반대 근거·적용 조건·기간은 전체 원문과 함께 별도 검토한다. 문장 함의·인과성·모순·전역 개체 존재는 판정하지 않는다. 진단이 비었다는 이유로 관계를 확정하지 않는다.

새 자료는 기존 개체 ID와 관계 종류부터 확인한다. 새 관계가 필요하면 실제 포함·제외 사례와 변경 이유를 검토하며, 자료 추가만으로 기존 ID·의미를 바꾸거나 전체 자료를 재분류하지 않는다. 현재 `kind:name` ID를 표시 이름에 맞춰 자동 변경하지 않는다. 확인된 정의·관계의 원문 변경은 기존 native 쓰기·독립 검토 경계를 따른다. DB를 읽지 못한 실행에서는 합성 입력 검증과 실제 의미 검증을 구분해 보고한다.

## 서로 다른 묶음

| 묶음 | 기준·소유자 | 안정성의 의미 |
| --- | --- | --- |
| 저장된 분류·기록 소속 | 문서 태그·회사 분야·기록 묶음의 저장 ID와 명시적 배정 | 확인된 분류 변경 전까지 의미와 식별자를 유지한다. 개인 기록의 자동 배정은 아래 기존 정책을 따른다. |
| 관계 군집 | 조회 응답의 현재 사용 가능한 관계를 Louvain으로 계산 | 같은 입력의 순서에는 안정적이다. 자료·연결·조회 범위가 바뀌면 군집도 바뀔 수 있다. |
| 관계 묶음 | 현재 군집 안의 연결망을 큰 허브 주변에서 접어 표시 | 연결망의 화면 요약이다. 대표 자료나 접힌 구성은 관계 변화에 따라 달라질 수 있다. |
| 폴더 묶음 | 같은 폴더 바로 아래에서 관계가 없는 원문을 접어 표시 | 경로에 따른 화면 요약이다. 폴더 이동과 표시 대상에 따라 달라진다. |
| 근접 묶음 | 관계 없는 지식의 좌표와 카메라의 표시 단계 | 화면 밀도를 줄인다. 의미 소속으로 저장하지 않는다. |

현재 Louvain은 분류 표식을 포함한 응답 노드를 대상으로 한다. `parent`·자기 연결·과거 연결·현재 사용 가능하지 않은 양 끝점은 계산에서 제외한다. 그 외 종류는 연결 하나당 가중치 1이며 같은 양 끝점의 여러 연결은 가중치를 합산한다. 방향은 계산에서 사용하지 않는다. 따라서 일반 참조, 근거, 복수 분류가 같은 계산에 영향을 준다.

계산 시드는 파생 폴더를 제외한 조회 응답의 문서·기록·분류 표식 ID와 부모 연결을 제외한 전체 연결에서 만들며, 과거 연결도 시드에 포함된다. 군집 ID는 정렬된 첫 구성원 ID에서 만들고 이름은 첫 분류 표식 또는 자료에서 가져온다. 기존 좌표 재사용은 기존 군집 소속을 고정하지 않는다. 자료 하나의 추가·삭제나 연결 상태 변화가 시드, 군집 구성, 식별자·색·대표 이름을 바꿀 수 있는 구조다. 이는 현재 관계 군집의 계약이며 고정 목적 그룹의 기준으로 삼기 어렵다.

앱 안의 표시 종류·상태 필터는 이미 계산한 모델을 좁힌다. 서버 검색·초점·반환 상한은 계산에 들어오는 응답 자체를 바꾼다. 부분 응답에서 만든 군집을 범위 전체의 영구 소속으로 저장하지 않는다.

## 저장된 목적 그룹

현재 계약과 기능 보존 조건에서 권장하는 구조는 **목적별 그룹의 지속 ID·정의·확인된 소속을 저장하고, 관계 군집과 화면 압축은 별도로 계산하는 것**이다. 같은 기존 `subjects` 저장소를 사용하며 별도 군집 원장을 만들지 않는다.

목적 그룹은 같은 문제·목적·결정 맥락으로 다시 찾고 함께 사용하는 자료의 단위다. 단어, 같은 폴더, 연결 수, 거리, 원문 라우터의 참조만으로 만들지 않는다. 기존 기록 묶음에서 실제 목적이 일치하면 그 저장 ID와 소속을 보존한다. 문서와 기록의 공동 목적 그룹이 필요할 때 기존 기록 묶음의 확장 가능성부터 검토한다.

그룹 정의에는 지속 ID, 소속 범위, 짧은 이름, 한 문장의 목적, 포함 기준, 제외 기준, 정의를 바꾸는 소유자가 필요하다. 이름만 저장하고 최근 구성원의 제목을 목적의 대용으로 삼지 않는다. ID는 이름·첫 구성원·구성원 해시·좌표에서 만들지 않으며 이름 변경에도 유지한다. 기존 이름만 있는 묶음은 정의 없음으로 보존한다. 정의된 묶음은 목적·포함·제외 기준과 revision을 저장하고 자동 판정 입력에도 같은 기준을 전달한다. 정의가 없는 기존 묶음만 이름과 최근 제목 최대 3개를 사용하는 이전 동작을 유지한다. 자동 적용 시 전체 후보의 ID·이름·정의·revision이 동일한지 확인하며 바뀌면 다시 검토한다. 이름이나 예시 변화로 목적을 다시 추측하는 별도 기준을 만들지 않는다.

지도의 기본 보기는 저장된 목적 소속이다. 목적 지도는 목적 소속과 선택한 폴더 연결만 그리고, 큰 묶음의 대표·구성원도 저장된 소속에서 정한다. 원문 참조의 증감이나 자료 상태 변화로 목적 대표를 다시 계산하지 않는다. 자료 상세의 들어오는·나가는 참조는 전체 관계 모델에서 읽는다. `묶음 기준`에서 관계 보기를 선택하면 기존 Louvain 군집을 탐색한다. 문서 소속은 native material UUID 또는 아직 native에 결합하지 않은 Git entity ID로 저장한다. 원문 scope/path나 화면의 binding alias가 소속 ID를 대신하지 않는다. 자료당 기본 소속은 0~1개다. 여러 맥락에서 쓰는 자료는 주된 작성·사용 목적이 명확할 때만 기본 소속을 고르고, 다른 맥락과의 관계·태그는 남긴다. 명확한 목적이 없거나 후보가 여럿이면 미분류 또는 후보 상태로 남긴다. 미분류는 동일 목적을 가진 거대 그룹이 아니다. 시각적으로 접을 수는 있지만 목적 소속이 있다고 표시하지 않는다.

문서 태그와 회사 분야는 복수 관점을 유지한다. 그룹과 경쟁하는 자동 우선순위(`subject` > `topic` > `area` 등)를 만들지 않는다. 현재 회사 분야 5개는 그대로 재사용하고 개인용 상위 분류를 추측해서 강제하지 않는다.

| 현재 회사 분야 | 목적을 구분할 때 사용할 정의 제안 |
| --- | --- |
| 전략·포트폴리오 | 무엇을 왜 할지, 어떤 사업·기회에 자원을 배분할지 결정하는 관점 |
| 시장·고객 이해 | 누구의 어떤 문제·수요·구매 조건을 해결할지 근거를 이해하는 관점 |
| 제품·서비스 제공 | 고객에게 제공할 가치와 해결 방법을 설계·구현·전달하는 관점 |
| 성장·판매·고객 관계 | 고객을 획득·전환·유지하고 판매·관계를 발전시키는 관점 |
| 경영 기반 | 조직·재무·법무·운영 기반을 유지하는 관점 |

위 분야는 복수 분류 축이다. 분야 하나에 속한 모든 자료가 하나의 목적 그룹이 되는 것은 아니다. 구체적인 그룹 이름과 포함·제외 사례는 실제 원문·기록의 목적을 확인한 뒤 정한다.

### 소속을 유지하거나 변경할 때

사용자가 확인한 소속은 새 자료, 일반 관계 추가·삭제, 이름 변경, 검색·필터, 카메라·화면 크기·표시 단계, 쪽 이동·펼치기 때문에 재배정하지 않는다. 소속은 사용자 변경, 실제 목적 변경 확인, 그룹의 명시적 합치기·나누기·삭제 때 바뀔 수 있으며 변경 이력을 남긴다. 합치기·나누기는 자동 관계 계산으로 실행하지 않는다. 현재는 기존 목적의 명시적 정의 수정 또는 새 목적 생성 후 자료별 소속 확인으로 수행한다. 별도의 원자적 일괄 합치기·나누기 API는 제공하지 않는다. 그룹 삭제는 문서와 기록을 보존하고 소속 해제 및 목적의 마지막 정의를 이력으로 남긴다.

개인 기록의 자동 배정·수동 선택·묶지 않음은 [기존 판단 정책](personal-memory-grouping.md)이 소유한다. 자동 배정은 내용 수정 시 재판단할 수 있다. `assigned`를 사용자 확인과 동일시하거나 자동 소속까지 영구 고정됐다고 표시하지 않는다. 하나의 기존 목적이 명확할 때 배정하고, 복수 후보·정보 부족은 후보 제시, 적합한 목적이 없으면 미분류를 유지한다. 새 그룹 제안이 생성·배정을 자동 승인하지 않는다.

신규 문서의 자동 판정은 [문서 판단 정책](document-grouping.md)이 소유한다. 양 앱 범위에서 현재 사용할 수 있는 canonical 문서를 정의된 기존 목적과 비교한다. 문서는 정의 없는 그룹에 자동 배정하거나 새 그룹을 제안하지 않는다. 수동 소속은 `manual`, 명시적 미분류는 `off`로 우선하며, 같은 미분류를 다시 저장해도 진행 중 자동 판정을 취소한다. 자동 상태·후보·이유는 목적 관리 화면에서 확인하고, **목적 자동 재검토**는 현재 원문과 소속 revision을 확인한 명시적 요청이다. 이전 소속은 재검토 요청으로 지우지 않는다.

서버는 3초마다 current metadata를 범위별 한 batch로 발견하고 분류 worker는 별도로 claim을 처리한다. 서버 중단 중 추가한 원문은 다음 시작에서 발견한다. `document-grouping-drain`은 발견과 처리 batch를 반복해 남은 작업을 소진한다. producer마다 별도 enqueue를 두지 않아 native import·Core 적용·수동 원문 편집·projection 준비·consumer binding·Git 갱신을 같은 identity와 currency 기준으로 검사한다. 복구 대기, 제외·삭제·restricted·미준비 원문은 모델에 전달하지 않는다.

같은 원문의 재발견과 terminal 상태의 revision만 전진한 경우 모델·소속·이력을 바꾸지 않는다. 자동 문서의 실제 내용 digest가 바뀌면 이전 소속을 보존한 채 다시 판단한다. 처리 중 원문 또는 전체 목적 정의 집합이 바뀌면 오래된 성공·실패를 폐기하고 최신 기준과 새 시도 횟수로 대기한다. 이미 끝난 자동 판정은 다른 자료·관계·새 그룹·projection 재생성으로 다시 실행하지 않는다. 진행 중 eligibility가 사라졌다 복구되어도 같은 bytes의 실패 횟수를 보존한다. claim별 UUID와 실제 시각의 lease를 확인하며 3회 중단 후에는 명시적 재검토가 필요하다. 일시적 native 적용·복구 대기는 시도 횟수를 소비하지 않는다.

원문 title/body 전체를 secret redaction한 뒤 판단하며 8192바이트로 자르지 않는다. 전체 판단 JSON이 65536바이트를 넘으면 모델을 호출하지 않고 수동 검토 이유를 표시한다. 유일한 유효 assign만 소속 이력을 추가한다. 후보·미분류·오류에는 기존 소속을 보존하고 지도와 목적 관리에 재확인을 표시한다. 관계를 만들거나 기존 그룹 ID를 재계산하지 않는다.

필터·검색·반환 상한은 화면의 구성원 수를 바꿀 수 있지만 저장된 그룹 ID·확인된 소속을 바꾸지 않는다. 전체 수와 현재 보이는 수를 구분하고, 일부만 반환됐다는 이유로 숨은 구성원 소속을 제거하지 않는다. 안정적인 그룹 조회는 범위 전체의 저장된 소속을 기준으로 해야 한다.

그룹의 의미 안정성은 모든 픽셀 좌표의 영구 고정을 요구하지 않는다. 같은 ID의 기존 배치는 재사용하되 충돌 회피에 필요한 이동은 허용한다. 대표 별·접기·쪽 이동·전체 펼치기는 표시 상태이며 그룹 소속을 쓰지 않는다. 기존 작은 원형 배치, 기본 접기, 큰 묶음의 12개 쪽 보기, 원래 화면 복원 계약을 유지한다.

### 저장과 적용 경계

목적 정의 수정은 현재 revision과 비교해 저장한다. 문서 소속 확인은 현재 원문 revision·digest, 소속 revision, 목적 revision과 분류 이유를 함께 받는다. 원문이나 정의가 먼저 바뀌면 저장을 거절하며 초안을 유지한다. 이후 원문·정의가 바뀌어도 소속을 자동 이동하지 않고 재확인 상태를 표시한다. 같은 현재 판단의 재저장은 이력을 추가하지 않는다. 정의와 소속 이력에는 당시 기준과 이유를 보존하고 원문 본문을 복제하지 않는다.

새 목적은 이름만 생성하거나 완전한 목적·포함·제외 기준을 한 요청에서 생성할 수 있다. 부분 정의는 저장하지 않는다. 생성 재시도는 동일한 생성 의도를 확인하며 현재의 이름·정의를 덮지 않는다. 이름만 만드는 기존 요청의 키 계산은 보존하고 완전 정의 요청은 별도 입력 형식으로 구분한다.

목적·소속 관리, 후보 검색과 이력은 요청한 시점에만 조회하며 한 쪽에 20개씩 표시한다. 그룹 전체 소속 수는 서버 검색·초점·반환 상한 전에 계산하고, 화면에 보이는 수와 구분한다. 목적과 관계 보기 전환은 현재 응답을 재사용하며 입력 중인 원문·목적 초안을 유지한다. 목적 보기는 저장된 소속으로, 관계 보기는 관계 군집으로 큰 묶음을 압축하며 두 보기 모두 12개씩 펼치기를 유지한다.

원문 링크는 native의 이미 파싱된 본문과 Git의 검증된 원문에서 파생한다. Git의 닫힌 첫 metadata만 제외하며 YAML 값 검증으로 기존 수입을 제한하지 않는다. 코드·이미지·외부 URL·질의·절대 경로·root 탈출·자기 링크와 native의 restricted/journal 대상은 연결로 승격하지 않는다. fragment는 대상 경로 확인에서 분리하고 percent-encoded UTF-8 이름은 정확히 해석한다. 실제 대상의 current 상태와 앱 범위가 확인된 연결만 같은 지도 snapshot에 포함한다. 상세에는 나가는 링크와 들어오는 참조를 구별하고 3D에는 방향 화살표를 표시한다. Memory 본문 링크는 formal evidence로 자동 치환하지 않는다.

native 갱신은 기존 `projection-status`/`project`의 현재 manifest 검증을 사용한다. 기존 Git metadata는 `context`의 `refresh-imported-references`에 앱 scope와 최대 100개의 entity ID·원문 revision·digest를 명시해 갱신한다. 잠근 현재 원문의 실제 SHA까지 검증하며 batch가 오래됐거나 범위·binding이 다르면 전부 거절한다. 갱신은 `source_records.reference_paths`만 바꾸고 원문·source 상태·관측 시각·generation·분류·기억·근거·이력을 변경하지 않는다. 향후 Git 수입은 같은 경로를 기존 transaction에서 파생한다.

지도에서 native 문서는 현재 revision·원문 digest에 일치하는 projection이 `searchable` 또는 `unavailable`일 때만 표시한다. 제외·삭제·미준비 projection은 집계·검색·초점·간선에서도 제외한다. 기존 binding이 있으면 과거 수입 사본으로 되돌아가지 않는다. 목적 소속 API도 같은 원문 경로 eligibility를 확인한다. 원문과 이력은 계속 보존한다.

문서 소속과 이력의 원장은 기존 `document_subjects`다. 과거 미분류나 늦은 binding을 신규 자동 요청으로 해석하지 않는다. 스키마 변경 이력과 DB별 적용 확인·업그레이드 절차는 [AGENTS.md의 백업과 복원 확인](../AGENTS.md#백업과-복원-확인)을 따른다.

| 검증 상황 | 통과 기준 |
| --- | --- |
| 같은 입력의 순서 변경·재조회 | 같은 저장 그룹 ID와 확인된 소속 |
| 무관한 자료 추가·일반 관계·과거 근거 상태 변경 | 기존 확인된 소속과 그룹 ID 유지 |
| 그룹 이름 변경·기존 첫 구성원 삭제 | 남은 구성원의 확인된 소속과 그룹 ID 유지 |
| 복수 태그·분야·프로젝트에 관련된 자료 | 기본 목적을 임의로 선택하지 않고 복수 탐색 관계 보존 |
| 수동 선택·묶지 않음·자동 내용 재판단 | 기존 개인 기록 정책 보존, 사용자 선택 우선 |
| 검색·초점·필터·반환 한도 | 전체 소속 보존, 표시 수와 전체 수 구분, 숨은 자료 삭제 추론 없음 |
| 그룹 나누기·합치기·삭제 | 명시적 변경과 이력, 원문·기록 보존 |
| 접기·쪽 보기·전체 펼치기·선택·복원·LOD | 그룹 소속 보존, 기존 화면 기능 회귀 없음 |

종류별 가중치 조정, 시드 고정, 이전 군집과의 유사도 매칭은 계산 결과를 덜 바뀌게 할 수는 있어도 목적의 타당성과 확인된 소속을 보장하지 않는다. 폴더나 거리를 기준으로 고정하면 구조·화면 묶음에는 맞지만 목적 그룹의 정의를 대신하지 못한다. 우선 저장된 분류·목적 소속을 사용하고 필요한 문서 확장만 검토하는 구조가, 자동 군집을 영구 분류로 승격하는 것보다 소유와 변경 이유를 명확하게 유지한다.

## 근거와 확인 범위

현재 계약은 [GraphLink와 군집·폴더 계산](../web/src/graph.ts), [화면 근접 요약](../web/src/nuclei.ts), [지도 API 투영](../src/graph.rs), [회사 분야와 문서 분류 검증](../src/domain.rs), [native ontology 검증](../crates/context-core/src/ontology.rs), [native 의미 관계 투영·조회](../src/context_projection.rs), [기록 묶음 저장](../src/memory.rs), [개인 자동 배정](../src/grouping.rs), [기존 개인 판단 정책](personal-memory-grouping.md)을 대조했다.

이 문서는 저장·조회·표시 계약이다. 개별 원문 분류의 검토 결과와 적용 여부는 해당 실행의 digest-bound 증거로 확인한다. 본문이 부족한 자료와 주된 목적이 불명확한 자료는 이유를 남기고 미분류로 유지한다. 관계가 없는 자료에도 임의의 연결을 만들지 않는다. 기능 검증과 실제 운영 적용은 각각 확인한 범위로 기록한다.

기록을 다른 기록의 근거로 선택한 경우, 소속만 바뀐 revision은 근거 내용 변경이 아니다. 고정한 revision 이후의 모든 이력이 명시적인 소속 변경이고 전체 document와 accepted 상태가 같을 때만 기존 근거를 현재로 유지한다. 이력의 `grouping_only` 표식으로 이를 구분하며, 표식이 없는 과거 이력까지 소속 변경으로 추정하지 않는다. 내용이 같은 correct도 기존대로 과거 generation을 무효화한다. 본문·제목·종류·적용 기간·근거·정제 provenance의 변경, 철회 또는 이력 누락은 재확인이 필요하다. 내용을 바꿨다가 원래대로 복원해도 과거 연결을 현재로 되살리지 않는다. 조회·지도·새 저장은 같은 판정을 쓰며 과거 pin과 bytes는 그대로 보존한다. 정제 후보 token은 소속을 포함한 입력의 변경을 따로 확인한다.

기록의 목적 소속 변경은 두 앱 범위에서 기존 `grouping-set`의 metadata transaction을 사용한다. 회사 범위는 manual/off만 허용하고 자동 분류 큐를 만들지 않는다. 내용이 같은 회사 기록 저장도 이 경로로 처리해 같은 소속은 CAS 확인 후 no-op이 된다. 기록 document JSON·검토 provenance·이전 근거 bytes는 재작성하지 않고 기존 이력·근거 pin을 이어간다.
