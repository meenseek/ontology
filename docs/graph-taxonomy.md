# 관계 taxonomy와 안정적인 그룹

이 문서는 지식 지도에서 관계와 묶음이 뜻하는 것, 목적별 그룹을 안정적으로 유지할 기준을 정의한다. 관계 목록과 현재 동작은 코드에서 확인한 계약이다. **고정 목적 그룹은 설계 제안이며 아직 구현하거나 기존 자료에 배정하지 않았다.** 원문 내용별 분류의 타당성은 실제 적용 전에 따로 검토한다.

## 현재 관계의 정의

문서와 기록은 지식이다. 문서 태그·기록 묶음·회사 분야는 분류 표식이고, 폴더는 경로에서 계산한 구조다. 분류 표식이나 접힌 대표 별을 별도 지식으로 세지 않는다.

| 관계 | 방향·대상 | 정의 | 그룹 판단에서의 한계 |
| --- | --- | --- | --- |
| 관련 자료 (`related`) | 문서 ↔ 문서. 저장된 수동 연결은 정렬된 양 끝점으로 보관하며, native 연결은 원문에서 참조한 자료로 향한다. | 두 자료를 함께 탐색할 이유가 있는 연결. native의 명시적 `related`와 설정으로 선택한 본문 링크도 이 종류로 투영한다. | 같은 목적이나 같은 그룹이라는 뜻은 아니다. 원문 라우터의 많은 참조도 각각의 자료 연결이다. |
| 출처 근거 (`evidence`) | 기록 → 문서 또는 근거로 사용할 수 있는 기록 | 기록이 참조한 자료와 리비전·내용을 연결한다. 현재 근거와 과거 근거를 구분한다. | 관련 자료와 구별한다. 연결 자체가 기록의 모든 주장을 사실로 확정하거나 같은 그룹 소속을 뜻하지 않는다. |
| 문서 태그 (`topic`) | 문서 → 태그 | 문서를 찾는 복수의 주제 관점. 문서당 0~10개, 앱 범위별 이름·저장 ID를 가진다. | 여러 태그가 공존한다. 같은 태그 하나만으로 단일 목적 그룹을 확정하지 않는다. |
| 기록 묶음 (`subject`) | 기록 → 묶음 | 같은 범위의 기록을 묶는 저장된 소속. 기록당 0~1개다. | 현재 문서는 이 소속의 대상이 아니다. 자동 배정과 사용자 선택의 변경 규칙도 다르다. |
| 회사 분야 (`area`) | 회사 문서 → 분야 | `meenseek` 문서를 5개 고정 사업 관점으로 분류한다. 복수 배정할 수 있다. | 업무 목적 그룹이나 개인 자료의 분류로 자동 치환하지 않는다. |
| 부모·소속 (`parent`) | 원문 또는 폴더 → 상위 폴더 | native scope와 경로에서 계산한 구조적 소속이다. | 사실 관계나 목적 소속이 아니다. 관계 군집 계산에서 제외한다. |

native 원문 안의 `ontology.relations`는 별도 층이다. 각 항목은 `from`·`type`·`to`로 두 의미 개체의 관계를 기술하며, 개체 ID는 `kind:name` 형식이다. 현재 `type`은 소문자 kebab-case 형식을 검증하고 의미별 허용 목록은 없다. 동일한 `from/type/to` 관계 항목의 중복은 금지하지만, 서로 다른 관계에서 같은 타입을 쓰는 것은 허용한다. 양 끝점의 형식 검증도 개체의 실재 참조나 주장 진실을 검증하는 것은 아니다. 예를 들어 테스트의 `supports`는 현재 Web 지도의 `evidence`와 자동으로 같은 뜻이 되지 않는다. 이 관계는 의미 개체 조회에서 출처 자료·리비전과 함께 반환하며, Web의 6종 자료 연결로 직접 표시하지 않는다.

추가 의미 관계를 도입할 때는 실제 사용 사례의 문장, 방향, 양 끝점의 대상, 근거 원문과 리비전, 같은 그룹을 뜻하는지 먼저 정의한다. 지원된다는 이유만으로 새로운 관계 이름이나 추측한 동의어를 대량 생성하지 않는다.

native의 다른 분류 축도 관계와 구분한다. `ontology: true`인 원문에서 다음 선택적 값을 검증한다.

| 축 | 현재 허용 값 | 의미 |
| --- | --- | --- |
| `type` | `project`, `business`, `decision`, `knowledge`, `writing`, `learning`, `entity` | 자료의 성격 |
| `domain` | `portfolio`, `product`, `business`, `engineering`, `writing`, `learning` | 자료를 다루는 영역 |
| `status` | `draft`, `active`, `archived` | 원문에 선언한 생애 상태 |
| `confidence` | `low`, `medium`, `high` | 원문에 선언한 확신 수준 |
| `entities` | `kind:name` 형식의 목록 | 자료에서 다루는 의미 개체 |
| `applies_to` | 비어 있지 않은 한 줄 값의 목록 | 적용할 맥락 |

원문의 `status`·`confidence`를 앱의 출처 확인 상태, 기록 저장 상태, 근거 검증 결과로 바꾸어 해석하지 않는다. `type`이나 `domain`만으로 같은 목적 소속을 추론하지 않는다. 앱의 `personal`·`meenseek` 조회 범위와 원문의 native scope도 별개이며, 조회 위치가 원문의 소속을 바꾸지 않는다.

## 서로 다른 묶음

| 묶음 | 기준·소유자 | 안정성의 의미 |
| --- | --- | --- |
| 저장된 분류·기록 소속 | 문서 태그·회사 분야·기록 묶음의 저장 ID와 명시적 배정 | 확인된 분류 변경 전까지 의미와 식별자를 유지한다. 개인 기록의 자동 배정은 아래 기존 정책을 따른다. |
| 관계 군집 | 조회 응답의 현재 사용 가능한 관계를 Louvain으로 계산 | 같은 입력의 순서에는 안정적이다. 자료·연결·조회 범위가 바뀌면 군집도 바뀔 수 있다. |
| 관계 묶음 | 현재 군집 안의 연결망을 큰 허브 주변에서 접어 표시 | 연결망의 화면 요약이다. 대표 자료나 접힌 구성은 관계 변화에 따라 달라질 수 있다. |
| 폴더 묶음 | 같은 폴더 바로 아래에서 관계가 없는 원문을 접어 표시 | 경로에 따른 화면 요약이다. 폴더 이동과 표시 대상에 따라 달라진다. |
| 근접 묶음 | 관계 없는 지식의 좌표와 카메라의 표시 단계 | 화면 밀도를 줄인다. 의미 소속으로 저장하지 않는다. |

현재 Louvain은 분류 표식을 포함한 응답 노드를 대상으로 한다. `parent`·자기 연결·과거 연결·현재 사용 가능하지 않은 양 끝점은 계산에서 제외한다. 그 외 종류는 연결 하나당 가중치 1이며 같은 양 끝점의 여러 연결은 가중치를 합산한다. 방향은 계산에서 사용하지 않는다. 따라서 일반 참조, 근거, 복수 분류가 같은 계산에 영향을 준다.

계산 시드는 파생 폴더를 제외한 조회 응답의 문서·기록·분류 표식 ID와 부모 연결을 제외한 전체 연결에서 만들며, 과거 연결도 시드에 포함된다. 군집 ID는 정렬된 첫 구성원 ID에서 만들고 이름은 첫 분류 표식 또는 자료에서 가져온다. 기존 좌표 재사용은 기존 군집 소속을 고정하지 않는다. 자료 하나의 추가·삭제나 연결 상태 변화가 시드, 군집 구성, 식별자·색·대표 이름을 바꿀 수 있는 구조다. 이는 현재 관계 군집의 계약이며 고정 목적 그룹의 기준으로 삼기 어렵다.

앱 안의 표시 종류·상태 필터는 이미 계산한 모델을 좁힌다. 서버 검색·초점·반환 상한은 계산에 들어오는 응답 자체를 바꾼다. 부분 응답에서 만든 군집을 범위 전체의 영구 소속으로 저장하지 않는다.

## 권장하는 고정 목적 그룹

현재 계약과 기능 보존 조건에서 권장하는 구조는 **목적별 그룹의 지속 ID·정의·확인된 소속을 저장하고, 관계 군집과 화면 압축은 별도로 계산하는 것**이다. 아래는 구현 전 적용할 설계 기준이다.

목적 그룹은 같은 문제·목적·결정 맥락으로 다시 찾고 함께 사용하는 자료의 단위다. 단어, 같은 폴더, 연결 수, 거리, 원문 라우터의 참조만으로 만들지 않는다. 기존 기록 묶음에서 실제 목적이 일치하면 그 저장 ID와 소속을 보존한다. 문서와 기록의 공동 목적 그룹이 필요할 때 기존 기록 묶음의 확장 가능성부터 검토한다.

그룹 정의에는 지속 ID, 소속 범위, 짧은 이름, 한 문장의 목적, 포함 기준, 제외 기준, 정의를 바꾸는 소유자가 필요하다. 이름만 저장하고 최근 구성원의 제목을 목적의 대용으로 삼지 않는다. ID는 이름·첫 구성원·구성원 해시·좌표에서 만들지 않으며 이름 변경에도 유지한다. 현재 기록 묶음은 저장 ID와 이름을 가지지만 목적·포함·제외 기준을 별도 필드로 저장하지 않는다. 현재 자동 판정 입력도 묶음 이름과 최근 기록의 예시 제목 최대 3개다. 정의를 확장하면 동일한 저장 정의와 리비전을 판정 입력에 전달하고 적용 시 현재 정의인지 검증해야 한다. 이름이나 예시 변화로 목적을 다시 추측하는 별도 기준을 만들지 않는다.

지도의 기본 소속은 자료당 0~1개 목적 그룹으로 제안한다. 여러 맥락에서 쓰는 자료는 주된 작성·사용 목적이 명확할 때만 기본 소속을 고르고, 다른 맥락과의 관계·태그는 남긴다. 명확한 목적이 없거나 후보가 여럿이면 미분류 또는 후보 상태로 남긴다. 미분류는 동일 목적을 가진 거대 그룹이 아니다. 시각적으로 접을 수는 있지만 목적 소속이 있다고 표시하지 않는다.

문서 태그와 회사 분야는 복수 관점을 유지한다. 그룹과 경쟁하는 자동 우선순위(`subject` > `topic` > `area` 등)를 만들지 않는다. 현재 회사 분야 5개는 그대로 재사용하고 개인용 상위 분류를 추측해서 강제하지 않는다.

| 현재 회사 분야 | 목적을 구분할 때 사용할 정의 제안 |
| --- | --- |
| 전략·포트폴리오 | 무엇을 왜 할지, 어떤 사업·기회에 자원을 배분할지 결정하는 관점 |
| 시장·고객 이해 | 누구의 어떤 문제·수요·구매 조건을 해결할지 근거를 이해하는 관점 |
| 제품·서비스 제공 | 고객에게 제공할 가치와 해결 방법을 설계·구현·전달하는 관점 |
| 성장·판매·고객 관계 | 고객을 획득·전환·유지하고 판매·관계를 발전시키는 관점 |
| 경영 기반 | 조직·재무·법무·운영 기반을 유지하는 관점 |

위 분야는 복수 분류 축이다. 분야 하나에 속한 모든 자료가 하나의 목적 그룹이 되는 것은 아니다. 구체적인 그룹 이름과 포함·제외 사례는 실제 원문·기록의 목적을 확인한 뒤 정한다.

### 소속을 유지하거나 변경할 때

사용자가 확인한 소속은 새 자료, 일반 관계 추가·삭제, 이름 변경, 검색·필터, 카메라·화면 크기·표시 단계, 쪽 이동·펼치기 때문에 재배정하지 않는다. 소속은 사용자 변경, 실제 목적 변경 확인, 그룹의 명시적 합치기·나누기·삭제 때 바뀔 수 있으며 변경 이력을 남긴다. 합치기·나누기의 ID 처리와 이전 소속 이력 보존은 실제 확장 설계에서 정의한다.

개인 기록의 자동 배정·수동 선택·묶지 않음은 [기존 판단 정책](personal-memory-grouping.md)이 소유한다. 자동 배정은 내용 수정 시 재판단할 수 있다. `assigned`를 사용자 확인과 동일시하거나 자동 소속까지 영구 고정됐다고 표시하지 않는다. 하나의 기존 목적이 명확할 때 배정하고, 복수 후보·정보 부족은 후보 제시, 적합한 목적이 없으면 미분류를 유지한다. 새 그룹 제안이 생성·배정을 자동 승인하지 않는다.

필터·검색·반환 상한은 화면의 구성원 수를 바꿀 수 있지만 저장된 그룹 ID·확인된 소속을 바꾸지 않는다. 전체 수와 현재 보이는 수를 구분하고, 일부만 반환됐다는 이유로 숨은 구성원 소속을 제거하지 않는다. 안정적인 그룹 조회는 범위 전체의 저장된 소속을 기준으로 해야 한다.

그룹의 의미 안정성은 모든 픽셀 좌표의 영구 고정을 요구하지 않는다. 같은 ID의 기존 배치는 재사용하되 충돌 회피에 필요한 이동은 허용한다. 대표 별·접기·쪽 이동·전체 펼치기는 표시 상태이며 그룹 소속을 쓰지 않는다. 기존 작은 원형 배치, 기본 접기, 큰 묶음의 12개 쪽 보기, 원래 화면 복원 계약을 유지한다.

### 적용 순서와 완료 기준

1. 현재 관계 종류·저장 소속·계산 군집·화면 요약의 정의를 유지한다. 연결의 의미를 바꾸거나 기존 자료를 일괄 재분류하지 않는다.
2. 실제 목적 그룹의 정의와 포함·제외 사례를 검토한다. 기존 저장 ID를 재사용하고, 문서를 공동 목적 그룹에 포함하려면 원문 소유자와 참조 저장 위치부터 정한다. native 원문은 native 경계를 유지하며 앱의 편의를 위해 복제하지 않는다. 원문 소속 참조는 `material_id` 등 소유 원문의 지속 식별자를 기준으로 설계한다. binding에 따라 달라질 수 있는 화면의 `c_`·`e_` ID를 원문의 영구 식별자로 저장하지 않는다. 현재 `subject`가 문서 소속까지 제공하는 것처럼 구현하지 않는다.
3. 확인된 그룹 조회·기본 소속 보기를 만들고 관계 군집 탐색을 보존한다. 저장 정의를 복제한 별도 군집 원장이나 부분 응답 기반 소속 저장을 먼저 만들지 않는다.

| 검증 상황 | 통과 기준 |
| --- | --- |
| 같은 입력의 순서 변경·재조회 | 같은 저장 그룹 ID와 확인된 소속 |
| 무관한 자료 추가·일반 관계·과거 근거 상태 변경 | 기존 확인된 소속과 그룹 ID 유지 |
| 그룹 이름 변경·기존 첫 구성원 삭제 | 남은 구성원의 확인된 소속과 그룹 ID 유지 |
| 복수 태그·분야·프로젝트에 관련된 자료 | 기본 목적을 임의로 선택하지 않고 복수 탐색 관계 보존 |
| 수동 선택·묶지 않음·자동 내용 재판단 | 기존 개인 기록 정책 보존, 사용자 선택 우선 |
| 검색·초점·필터·반환 한도 | 전체 소속 보존, 표시 수와 전체 수 구분, 숨은 자료 삭제 추론 없음 |
| 그룹 나누기·합치기·삭제 | 명시적 변경과 이력, 원문·기록 보존 |
| 접기·쪽 보기·전체 펼치기·선택·복원·LOD | 그룹 소속 보존, 기존 화면 기능 회귀 없음 |

종류별 가중치 조정, 시드 고정, 이전 군집과의 유사도 매칭은 계산 결과를 덜 바뀌게 할 수는 있어도 목적의 타당성과 확인된 소속을 보장하지 않는다. 폴더나 거리를 기준으로 고정하면 구조·화면 묶음에는 맞지만 목적 그룹의 정의를 대신하지 못한다. 우선 저장된 분류·목적 소속을 사용하고 필요한 문서 확장만 검토하는 구조가, 자동 군집을 영구 분류로 승격하는 것보다 소유와 변경 이유를 명확하게 유지한다.

## 근거와 확인 범위

현재 계약은 [GraphLink와 군집·폴더 계산](../web/src/graph.ts), [화면 근접 요약](../web/src/nuclei.ts), [지도 API 투영](../src/graph.rs), [회사 분야와 문서 분류 검증](../src/domain.rs), [native ontology 검증](../crates/context-core/src/ontology.rs), [native 의미 관계 투영·조회](../src/context_projection.rs), [기록 묶음 저장](../src/memory.rs), [개인 자동 배정](../src/grouping.rs), [기존 개인 판단 정책](personal-memory-grouping.md)을 대조했다.

이 정의는 자료 본문의 의미를 전수 판정한 결과나 고정 그룹 기능의 구현 완료 보고가 아니다. 기존 그룹 전체의 개별 목적, 제외된 검색 투영의 원문 의미, 문서까지 포함한 저장 경계와 합치기·나누기 기능은 실제 적용 전에 확인할 범위다. 의미 정의만으로 자동 군집의 안정성이나 화면 회귀 검증이 완료됐다고 보지 않는다.
